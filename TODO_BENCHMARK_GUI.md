## 2. Metric cần ghi và ý nghĩa

| Metric                                                | Lấy ở đâu                                                              | Đọc như thế nào                                                                                                                                         |
| ----------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `median_ms` (p50), `p95_ms`                           | `READ_SUMMARY`, `WRITE_SUMMARY`; 25 mẫu sau 2 warmup                   | p50 là trung vị; p95 cho thấy phần đuôi chậm. Dùng 25 mẫu gốc để kiểm lại; một lần bấm Explain không thay thế được.                                     |
| `logical reads`, SQL CPU/elapsed                      | `STATISTICS IO/TIME` trong `*_diagnostics.sql`                         | Trang 8 KB được đọc trong bộ nhớ, CPU/elapsed của truy vấn chẩn đoán. Khác với ms benchmark; xem cùng actual plan.                                      |
| `totalKeysExamined`, `totalDocsExamined`, `nReturned` | Compass Explain → Raw Output hoặc `READ_PLAN` Mongo                    | Lượng key/document đã xét so với số trả về; xem `COLLSCAN`, `IXSCAN`, `FETCH`, `SORT`, `TEXT_MATCH`, `isMultiKey`. Explain là phép đo chẩn đoán riêng.  |
| `index_build_ms`, `index_storage_bytes`               | `INDEX_BUILD`, `INDEX_INVENTORY`, `STORAGE`                            | Thời gian tạo index và dung lượng index; SQL đếm page/allocated/used tùy UC, Mongo dùng `indexSizes`. Không mặc nhiên coi hai byte counter tương đương. |
| INSERT rows/s, UPDATE median ms                       | `WRITE_SUMMARY` trên bản sao ghi độc lập                               | Chi phí duy trì index khi ghi; kiểm tra số dòng bị tác động và loại ghi trước khi diễn giải.                                                            |
| Correctness / freshness                               | `COPY_READY`, `READ_IDS`, checksum/parity, `FRESHNESS`, `RUN_COMPLETE` | Cấu hình A/B/C phải trả cùng kết quả khi ngữ nghĩa bằng nhau. UC4 còn đo thời gian full-text thấy dữ liệu mới.                                          |

**Indexing structure:** SQL nonclustered rowstore và index thường của Mongo sắp xếp các key để tìm một khoảng; thứ tự trường quan trọng. `INCLUDE` của SQL nằm ở leaf để trả cột mà không mở rộng khóa tìm kiếm; Mongo không có `INCLUDE`, nên UC3 thêm trường vào compound key. Filtered/partial chỉ chứa bản ghi thỏa điều kiện và không phù hợp truy vấn cần cả bản ghi ngoài điều kiện. Full-text/text dùng token/inverted access thay cho dò chuỗi con. Columnstore nén dữ liệu theo cột trong rowgroup để đọc các cột cần tổng hợp; point lookup không mặc nhiên nhanh. Multikey mở rộng một mảng thành các key, nên một kết quả hai tag có thể vẫn cần `FETCH` để kiểm điều kiện còn lại. Kết luận cuối cùng phải dựa trên plan thật.

## 5. Kiểm tra trực quan MongoDB Server bằng Compass

Compass kết nối **server thật**, làm các bước sau trên **collection bản sao**, không thao tác index trên `big_table_*` hoặc seed. Để tạo bản sao qua giao diện: mở source → **Aggregations** → thêm stage cuối `{ $out: "<tên-bản-sao>" }` → Run và xác nhận ghi; chỉ làm khi tên đích chưa tồn tại, vì `$out` có thể thay thế collection đích. Kiểm tra count và tab Indexes của từng bản sao; A chỉ có `_id_`. Với UC4/UC6, tên bản sao A/C và write khớp `mongo/uc4_text/uc4_run.js`, `mongo/uc6_multikey/uc6_run.js`.

- [ ] **UC1:** Trên `uc1_bench_100K`, query bar dùng Filter `{"OWNER":"SYS","OBJECT_TYPE":"TABLE","OBJECT_ID":16}` cho U1a. Dùng hai trường đầu cho U1b; bỏ `OWNER` cho U1c; U1d Filter `{"OWNER":"CTXSYS"}`, Sort `{"OBJECT_TYPE":1,"OBJECT_ID":1}`. Project `{"_id":0,"ID":1,"OWNER":1,"OBJECT_TYPE":1,"OBJECT_ID":1}`. Xem Explain ở A; tab Indexes tạo B `OWNER: Ascending`, xem Explain; xóa **chỉ** B, tạo C theo thứ tự `OWNER`, `OBJECT_TYPE`, `OBJECT_ID`, xem Explain lại. Đối chiếu count/keys/docs/sort.
- [ ] **UC2:** Làm cho `uc2_bench_100K` và `uc2_bench_1000K`. Filter mẫu `{"TEMPORARY":"Y","OBJECT_TYPE":"TABLE","OBJECT_ID":{"$gte":1,"$lte":10000}}`; lặp với `N`. B: index `OBJECT_TYPE, OBJECT_ID, TEMPORARY` Ascending. C: cùng key order, thêm Partial filter expression `{"TEMPORARY":"Y"}` trong dialog Create Index. Xem Explain cho Y và N, cùng kích thước index ở tab Indexes.
- [ ] **UC3:** `uc3_bench_100K` / `uc3_bench_1000K`: Filter theo `OBJECT_ID` lấy đúng giá trị/range từ `mongo/uc3_covered/uc3_run.js`; Project `{"_id":0,"ID":1,"OWNER":1,"OBJECT_NAME":1,"OBJECT_TYPE":1}`. B tạo `OBJECT_ID`; C thay bằng `OBJECT_ID, ID, OWNER, OBJECT_NAME, OBJECT_TYPE`. Xem C còn `FETCH` và `totalDocsExamined` không; đừng gọi “covered” chỉ vì có IXSCAN.
- [ ] **UC4:** Trên `uc4_read_A`, dùng regex `{ "BODY": { "$regex": "climate", "$options": "i" } }`; trên `uc4_read_C`, tạo text index `BODY: Text` tên `ix_uc4_body_text`. MongoDB mặc định dùng `default_language: "english"`; kiểm tra thuộc tính index sau khi tạo để khớp script, rồi Filter `{ "$text": { "$search": "climate" } }`. Cụm từ dùng dấu ngoặc kép bên trong `$search`, ví dụ `"\"climate change\""`. Lặp các từ/cụm từ trong script. Lưu/export `DOC_ID` đầy đủ và so **tập ID**; không coi A/C mặc nhiên tương đương.
- [ ] **UC5:** Không có bước Mongo.
- [ ] **UC6:** Trên `uc6_read_A` / `uc6_read_C`, Filter `{"tags":"type:TABLE"}` và `{"tags":{"$all":["owner:SYS","type:TABLE"]}}`; C tạo `tags: Ascending`. Explain phải kiểm `isMultiKey`, IXSCAN/FETCH, keys/docs và parent ID đầy đủ. Đừng suy ra hai tag đều được giải bằng index chỉ từ tên IXSCAN.

Ở mỗi cấu hình, vào **Documents → Filter/Project/Sort → Explain → Raw Output**; chụp/lưu JSON plan kèm tên UC, query và A/B/C. Compass hỗ trợ tạo index, partial filter, query và Explain qua UI. **Compass Explain chỉ là phép chẩn đoán một truy vấn**, không tạo tự động 2 warmup + 25 mẫu, không bảo đảm render/scroll hết cursor, cũng không đo chính xác 20 batch INSERT/UPDATE của protocol. Vì vậy số “Execution time” trong Explain chỉ để hiểu plan, **không ghi vào `READ_SUMMARY` của benchmark**. UI tạo index cũng không có cùng mốc thời gian build do script đo; nếu chỉ thao tác Compass, ghi build time là “chưa đo”.
